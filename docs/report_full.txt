Abstract
This report presents multicore scaling and benchmarking of two families of lightweight
RV32I soft-core processors running on a PYNQ-Z2 (Zynq-7020) FPGA. The designs
include a 4-stage pipelined core scaled to 2, 4, and 8 cores, and a 6-stage multicycle
multicore architecture. The cores execute a uniform bare-metal workload without libc
library support and utilise a mailbox-based synchronisation scheme along with shared
BRAM. The data memory is partitioned per core to maintain architectural parity
across all cores.
Additionally, the performance is evaluated using MiBench integer
benchmarks such as Basicmath, Bitcount, Qsort, Stringsearch, FFT, and IFFT. Ex-
perimental results demonstrate that the 4-stage multicore architecture achieves much
higher performance and efficiency across all core counts than multicycle cores. The
multicore speedup is up to 5.98 times for the 8-core configuration. Furthermore, the
4-stage architecture demonstrates superior resource utilization, consuming only 28,591
LUTs and 1.63 W of total power in the 8-core configuration, compared to 43,731 LUTs
and 1.69 W for the 6-stage design. As a practical application, a lightweight Convolu-
tional Neural Network (CNN) for fruit image classification is deployed on the 4-core
system using int8 quantized inference, correctly classifying all five fruit categories and
validating the architecture for embedded AI workloads.
Keywords: RISC-V, multicore processors, FPGA, parallel performance, embedded
systems, CNN inference, int8 quantization

Chapter 1
Introduction
L
ightweight RISC-V soft processors have shown substantial research interest in
FPGA-based research and education environments owing to their module nature
and open ISA. Several open-source RV32I processor cores have been implemented to
support embedded systems and other computing systems with limited resources. These
processor cores include PicoRV32, SERV, NEORV32, Ibex, and the Sodor family of
teaching processor cores [1, 2, 3, 4, 5].
Most existing research has focused only on the implementation of a single-core proces-
sor or on evaluating a processor individually across various experimental environments.
Even though some research studies have explored multicore versions of the processor,
the evaluation approaches used across studies differ substantially. It becomes difficult
to compare the performance of various processor architectures with FPGA devices.
Moreover, most popular RISC-V processor research platforms, including Rocket Chip,
are designed to support only high-performance systems running Linux [6].
Recent
studies have extensively evaluated RISC-V soft-cores on FPGAs. H¨oller et al. [7] and
Makni et al. [8] provided comprehensive comparisons of various open-source cores,
highlighting area and throughput trade-offs. Furthermore, recent works have explored
hardware-software co-design for multi-threaded RISC-V systems [9] and evaluated spe-
cific cores like NEORV32 and CVA6 for embedded applications [10, 11]. Other studies
have compared high-performance RISC-V processors against established embedded
platforms [12] and proposed optimized pipelined soft processors like RVCoreP [13].
These processor research platforms are highly efficient, but they cannot support
lightweight FPGA-based research environments that require only basic multicore pro-
cessor evaluation. There are a limited number of research studies that validate the per-
formance of lightweight RV32I multicore processor architectures with the same software
and hardware environments on FPGA devices.

1.1
Research Gap and Novel Contributions
In spite of the maturity of the RISC-V ecosystem, it is observed that lightweight RV32I
soft cores are mostly described in the form of single-core architectures in instructional
materials and open-source resources [5, 1, 4, 14, 15]. Even though there exist mul-
ticore variants of these architectures, evaluation methodologies also show variations
and inconsistencies in build configurations, memory models, runtime environments,
and performance evaluation approaches [16]. Consequently, there is a need for board
validation-based experimental research on the evaluation of different lightweight RV32I
multicore architectures under similar experimental conditions.
The contributions of this research can be summarised as follows:
• FPGA-based multicore scaling of a 4-stage RV32I pipeline.
The
lightweight four-stage in-order RV32I core is extended from a single core to a
multicore environment with 2, 4, and 8 cores on the PYNQ-Z2 FPGA platform.
• Fair architectural comparison with a 6-stage multicycle multicore. The
proposed four-stage multicore design is compared with an existing six-stage mul-
ticycle RV32I multicore design under the same runtime environment and condi-
tions.
• Unified benchmarking framework for FPGA-based multicore evalua-
tion. The performance evaluation uses a unified benchmarking environment em-
ploying bare-metal applications, mailbox synchronization, and BRAM memory
partitioning.
• Comprehensive experimental evaluation using MiBench workloads.
The design is evaluated using Basicmath, Bitcount, Qsort, Stringsearch, FFT,
and IFFT from the MiBench suite.
• Quantitative analysis of multicore performance metrics. Performance
metrics are quantified using hardware performance counters.
• Investigation of FPGA resource utilization and scalability. LUT, FF,
BRAM, and power consumption are quantified for all configurations.
• CNN inference application on the multicore system. A lightweight int8-
quantized CNN for fruit classification is deployed on the 4-core system, demon-
strating the platform’s viability for embedded AI workloads.

Chapter 2
Literature Review
A variety of lightweight RV32I soft core implementations have been proposed for
FPGA-based systems and educational purposes. These implementations focus on small
size, bare-metal programming models, and tight coupling of the memories to allow repli-
cation in simple multicore configurations. Some examples include PicoRV32, SERV,
NEORV32, Ibex, Sodor, FemtoRV, and PULPino [1, 2, 3, 4, 5, 14, 15].
Despite the differences in pipeline length, programming model, and design flexibility,
the majority of reported results focus on single-core implementations or do not present
multicore benchmarking on actual hardware platforms. In the present contribution, a
comparison between two RV32I core implementations is presented after validation on
actual hardware platforms.

3.1
System Architecture Overview
The global architecture of the proposed RV32I multicore system implemented on the
PYNQ-Z2 FPGA platform is depicted in Figure 3.1. A Zynq Processing System (PS)
acts as a host controller managing all RV32I cores via an AXI-based interconnect. Each
RV32I core runs independently with a dedicated BRAM window for local data storage
and uses a mailbox-based synchronisation mechanism. The host processor initialises
all benchmark workloads, loads program binaries into the instruction memory of all
worker cores, and sends tasks via a mailbox descriptor stored in BRAM. Each core
runs its workload independently and provides execution metrics such as instruction
and cycle counts. BRAM memory is equally partitioned between all cores: 128 KiB
per core for a two-core system, 64 KiB for a four-core system, and 32 KiB for an
eight-core system.

3.3
Memory and Interconnect Organization
Each RV32I core is assigned a fixed, private BRAM window for data.
The same
memory partitioning is used for both processor families to maintain parity.
• Per-core BRAM size: N=2: 128 KiB; N=4: 64 KiB; N=8: 32 KiB.
• Base address: CORE BASE(i) = 0x40000000 + i × SN.
• In-window layout:
0x0000--0x1FFF: stack
0x2000:
mailbox (MB[8]=#jobs, MB[0]=done, MB[1--4]=inst/cyc lo/hi)
0x2100:
job descriptors + data buffers (64-byte aligned)
Each core has a single AXI4 master interface to access data BRAM and a single AXI4-
Lite interface. The Zynq PS uses a shared interconnect to interface with the cores.
Address windows are allocated via the Vivado Address Editor [18, 19]. The 2-core
block diagram is shown in Figure 3.2.

3.6
Benchmarks, Inputs and Benchmarking Metrics
Integer kernels from the MiBench suite — Basicmath, Bitcount, Qsort, Stringsearch,
FFT, and IFFT — are evaluated [20]. Their inputs are identical across all configura-
tions and small enough to fit within BRAM. Performance metrics are:
• WALL: Maximum cycle count across all cores.
• Parallel IPC: Total instructions executed divided by WALL.
• Total MIPS: Parallel IPC × achieved clock frequency.
• Execution time: WALL divided by clock frequency.
• Speedup and Efficiency: Relative to the 2-core baseline of each family.

4.2
Results and Discussion
We compare two RV32I multicore families on the same board: (i) a 4-stage in-order
pipeline scaled to 2, 4, and 8 cores, and (ii) a 6-stage multicycle multicore. Both use the
same mailbox + shared-BRAM runtime and the same benchmark binaries. Per-core
data BRAM windows match across families at each N.
Table 4.2 shows the Parallel IPC, Total MIPS, Time, Speedup, and Efficiency for all
kernels at the achieved clock rates.
The main observations are:
• Throughput: The 4-stage cores exhibit higher Parallel IPC for all core counts,
resulting in higher Total MIPS at the achieved clock rates.
• Scaling: Efficiency decreases as N increases for both cores due to interconnec-
t/BRAM constraints. However, the 4-stage configuration retains higher efficiency
throughout.

4.4.1
Overview and Motivation
The benchmark evaluation in Sections 4.1–4.3 established that the four-stage RV32I
multicore architecture achieves competitive instruction throughput on integer work-
loads.
However, Basicmath, Bitcount, and FFT are synthetic kernels.
A natural
extension is to validate the platform on a real-world inference workload that mirrors
the compute patterns of embedded AI at the edge.
CNN inference is well-suited to this architecture because convolution is a data-parallel,
integer multiply-accumulate (MAC) dominated operation identical in structure to the
Matmul benchmark. Each output channel can be computed independently, making it
straightforward to partition the work across cores using the same mailbox and BRAM
framework. Post-training int8 quantization eliminates the need for floating-point hard-
ware, which the RV32I ISA does not provide natively.
The classification task uses the Fruits-360 dataset [23], resized to 32 × 32 pixels.
Five fruit classes are considered: Apple Red 1, Banana 1, Mango 1, Orange 1, and
Pomegranate 1.

5.1
Discussion and Comparison with Related Work
The results presented in Chapter 4 reveal several important trends for the performance
of lightweight RISC-V multicore architectures on FPGAs. The pipelined architecture
outperforms the six-stage multicycle architecture for all core counts. Although the
multicycle architecture achieves a marginally higher clock speed in isolation, its in-
struction throughput is insufficient to compete with the performance of the four-stage
architecture across any tested workload.
The scalability of the two architectures also shows a dramatic difference. While the
four-stage architecture scales well as the number of cores increases from 2 to 8, the six-
stage multicycle architecture shows significant difficulty scaling. This is attributable
to high traffic on the AXI bus and BRAMs, which limits the parallel efficiency of the
cores at higher N.
Workload characteristics play a significant role in scalability for both architectures.
Compute-intensive workloads such as Basicmath, FFT, and Matmul scale efficiently
because the data can be cleanly partitioned and there is zero inter-core communica-
tion during computation. Irregular workloads such as Qsort and Stringsearch exhibit
unstable performance owing to load imbalance when the host aggregates results.
These results are consistent with findings from the broader RISC-V soft-core literature.
Studies evaluating PicoRV32, Ibex, NEORV32, and VexRiscv have consistently shown
that maximizing instruction throughput per cycle yields the greatest performance im-
provement when memory bandwidth is the primary bottleneck [1, 4, 17, 10]. Studies
examining Sodor cores have shown that minimizing pipeline stages can achieve a better
area–performance trade-off on FPGAs where clock frequency is ultimately limited by
FPGA fabric delay [5].
20
chapter: 05
21
The principal conclusion is that in a shared-memory multicore system based on RV32I
implemented on an FPGA, optimizing for instruction throughput provides substan-
tially greater return on investment than optimizing for clock frequency. The four-stage
pipelined architecture is therefore the more advisable design choice for this class of
system.
5.2
CNN Inference as a Workload Characterization
The CNN inference application introduced in Section 4.4 provides a complementary
perspective on the multicore platform by exercising it with a structured, hierarchical
workload rather than isolated integer kernels.
Compute pattern similarity with MiBench. The convolution layers are struc-
turally equivalent to the Matmul benchmark. A 3×3 convolution is a sliding-window
matrix multiply over the input feature map. The Matmul results in Table 4.2 demon-
strated the highest scaling efficiency (13.59× at 8 cores for 4-stage), which predicted
that convolution workloads would also benefit strongly from core replication. The CNN
results confirm this prediction: both Conv1 and Conv2 achieve near-linear throughput
scaling across the four cores when measured by output channels produced per unit
time.
Data parallelism. Like Basicmath and Bitcount, the CNN convolution layers exhibit
perfect data parallelism when partitioned by output channel. Each core computes its
assigned output channels entirely from data in its private BRAM window, with zero
inter-core communication during computation. The only synchronisation points are
the mailbox assertions at the start and end of each layer, which are identical to the
synchronisation model used in the MiBench evaluation.
Memory footprint pressure. Unlike MiBench benchmarks which comfortably fit
in 32 KiB, the CNN workload operates close to the 64 KiB per-core BRAM limit.
The Conv2 layer packs 8 × 16 × 16 input features plus 4 × 8 × 3 × 3 weight filters plus
output channels plus scale factors into approximately 15 KiB per core. A deeper model
or larger input resolution would exceed the BRAM budget without external memory
access.
Heterogeneous execution model. Unlike the MiBench evaluation where the ARM
processor only orchestrates, the CNN workload requires the ARM to perform actual
computation for the pooling and fully-connected layers. This hybrid approach is nec-
essary because the RV32I cores lack hardware FPU support, and the FC layers involve
soft-float arithmetic that is significantly cheaper on the ARM Cortex-A9.
Soft-float bottleneck. The dequantization step in the RV32I worker (real val =
acc * input scale * w scale) uses software floating-point emulation.

5.3
Towards an AI Accelerator: Architectural Extensions
The current implementation demonstrates that the four-stage RV32I multicore sys-
tem can correctly execute CNN inference by leveraging int8 quantization and a host-
managed pipeline. However, the absence of hardware multiply and FPU support means
that a significant fraction of worker execution time is consumed by software arithmetic
routines rather than productive MAC operations. This section proposes a set of con-
crete architectural extensions that would transform the general-purpose RV32I multi-
core into a lightweight dedicated AI accelerator. The extensions are ordered from low
implementation cost to high, with each building upon the preceding one.
5.3.1
Custom Multiply-Accumulate (MAC) Instruction
Current bottleneck. A single 3×3 convolution pixel requires 9 multiply-accumulate
operations. On RV32I without the M extension, software multiplication requires ap-
proximately 30 cycles per operation. Even with the M extension, a multiply-accumulate
requires three separate instructions: mul, add, and a store.
Proposed extension. A fused MAC instruction is added to the execute stage of the
4-stage pipeline:
mac rd, rs1, rs2
# rd = rd + (rs1 * rs2),
single cycle
Implementation. The Zynq-7020 provides 220 DSP48E1 slices, each containing a
25×18-bit multiplier with built-in accumulator. Allocating one DSP per core (4 slices
total, 1.8% of available DSPs) enables single-cycle fused multiply-accumulate with no
impact on the existing pipeline stages.
Expected improvement. The 3×3 convolution inner loop currently requires approx-
imately 270 cycles per output pixel (9 multiplications × 30 cycles). With single-cycle
fused MAC, this reduces to approximately 27 cycles — a 10× speedup on the convo-
lution kernel. The Amdahl speedup for the full inference pass depends on the fraction
of time spent in convolution, but given that Conv1 and Conv2 dominate, an overall
5–8× end-to-end improvement is expected.
ISA alignment. This proposal aligns with the RISC-V “P” (Packed SIMD) extension
draft [26], which defines similar fused MAC instructions for DSP-class workloads.

5.3.2
SIMD Int8 Packed Operations
Current bottleneck. Each int8 multiply-accumulate widens both operands to int32
before the operation, wasting 75% of the 32-bit datapath width. Four independent
int8 multiplications could in principle be computed simultaneously.
Proposed extension. Pack 4×int8 values into a single 32-bit register and perform a
4-way dot product in one instruction:
dot4 rd, rs1, rs2
# rd += rs1[0]*rs2[0] + rs1[1]*rs2[1]
#
+ rs1[2]*rs2[2] + rs1[3]*rs2[3]
where rs1 and rs2 each contain four packed int8 values in bytes [31 : 24], [23 : 16],
[15 : 8], [7 : 0].
Impact. A 3×3 convolution kernel (9 MACs) reduces to 3 SIMD instructions (each
processing 4 pairs, with one position zero-padded). Combined with the single-cycle
MAC from Section 5.3.1, this yields an additional 4× throughput improvement over
scalar fused MAC.
Implementation cost. Four DSP48E1 slices per core are required, consuming 16
slices across all 4 cores (7.3% of the Zynq-7020 total). ARM NEON, the RISC-V Zvbb
extension, and Intel VNNI all provide similar packed int8 dot-product primitives for
neural network acceleration [25].
5.3.3
Systolic Array Co-Processor
Concept. Rather than modifying the RV32I cores, a dedicated systolic array IP block
is instantiated alongside the cores on the FPGA fabric. The ARM host dispatches
convolution jobs to the systolic array via AXI, and the array writes results directly to
a shared BRAM region.
Architecture. A systolic array consists of an M × M grid of processing elements
(PEs). Each PE performs one multiply-accumulate per clock cycle and passes partial
sums to its neighbour. Data flows through the PE grid in pipelined waves, achieving
up to M2 MACs per cycle.
Sizing for the PYNQ-Z2. A modest 4×4 systolic array using 16 DSP48E1 slices
(7.3% of available) computes 16 MACs per cycle. For the Conv2 layer (which requires
8×16×16×3×3 = 18,432 MAC operations per full output), this provides approximately
1,152 cycles versus approximately 73,000 cycles on the current software path — a 63×
speedup for that layer alone. This is the core principle behind the Google Tensor
Processing Unit (TPU) [27], implemented here at a scale appropriate to the PYNQ-Z2
resource budget.

ReLU. The function max(x, 0) is implementable as a single multiplexer in the pipeline

Sigmoid/Tanh for RNN workloads. These non-linear functions can be approxi-

5.3.5
DMA-Based Data Streaming
Current bottleneck.
The ARM transfers input data and weights to each core’s
BRAM using programmed I/O over AXI. For the Conv2 layer, the ARM writes ap-
proximately 15 KiB×4 cores = 60 KiB before each layer can begin. This programmed
I/O transfer is serialized and occupies the ARM processor, which cannot overlap with
other computation.
Proposed solution.
Use the Zynq PS DMA controller (AXI-DMA IP block) to
transfer data blocks from DDR3 SDRAM to each core’s BRAM:
1. ARM prepares all four core data buffers in DDR3 during the preceding layer’s
computation.
2. Issues four DMA transfer descriptors simultaneously, one per core.
3. The DMA engine handles AXI burst protocol, freeing the ARM for pooling com-
putation.
Expected improvement. AXI burst transfers on the Zynq-7020 achieve approxi-
mately 1–2 GB/s (64-bit bus at 150 MHz), compared to approximately 50–100 MB/s
for programmed I/O byte writes. The data-loading phase for Conv2 would reduce from
approximately 1 ms to approximately 30 µs, effectively eliminating the data transfer
overhead from the critical path.

5.3.6
Binary Neural Networks for Multiply-Free Inference
Concept. Binary Neural Networks (BNNs) [28] constrain all weights and activations
to {−1, +1}, eliminating all multiplication operations. The MAC operation degener-
ates to:
XNOR(ab, wb) −→result bit;
popcount(result register) −→accumulation
(5.1)
Why this is architecturally ideal for RV32I. The RV32I ISA already provides
xor (for XNOR) and bitwise-and operations natively. A 32-bit register holds 32 bi-
nary weights, and a single xor followed by a software popcount computes 32 MACs
simultaneously. This approach requires no M extension, no DSP slices, and no FPU
— only a new compiled worker binary with the binary-constrained kernels [29].
Accuracy trade-off. BNNs typically lose 2–5% accuracy compared to int8 models
on image classification tasks. Given that the float32 FruitCNNSmall achieves >98%
accuracy, a BNN variant would be expected to achieve >93% on the same task —
adequate for a fruit classification application. Retraining with the straight-through
estimator [28] would be required, but no hardware modifications are needed.

Chapter 6
Conclusions and Future Work
6.1
Summary of Contributions
This report presented a controlled and reproducible evaluation of two lightweight RISC-
V RV32I multicore processor designs on the PYNQ-Z2 (Zynq-7020) FPGA platform,
extended with a practical CNN inference application.
The contributions are sum-
marised as follows:
• Multicore scaling of a 4-stage RV32I pipeline. The lightweight four-stage
in-order RV32I core was extended from a single core to a multicore environment of
2, 4, and 8 cores on the PYNQ-Z2, using a unified mailbox-based synchronisation
and shared BRAM framework.
• Fair architectural comparison with a 6-stage multicycle multicore. The
proposed four-stage multicore design was compared against an existing six-stage
multicycle RV32I multicore under identical runtime conditions, binaries, memory
partitioning, and performance measurement methodology. The 4-stage design
achieves up to 5.98× speedup at 8 cores, consuming only 28,591 LUTs and 1.63
W versus 43,731 LUTs and 1.69 W for the 6-stage design.
• Unified benchmarking framework. A bare-metal benchmarking framework
was developed using mailbox synchronisation, per-core BRAM partitioning, and
hardware performance counters, enabling reproducible evaluation of MiBench
workloads: Basicmath, Bitcount, Qsort, Stringsearch, FFT, IFFT, and Matmul.
• CNN inference application.
An int8-quantized lightweight CNN (FruitC-
NNSmall, ∼34,357 parameters) was deployed on the 4-core system for fruit im-
age classification across five categories. The system correctly classifies all five
fruit classes, validating the multicore architecture for real-world embedded AI
workloads using balanced activation calibration and a host-worker pipeline.

• Architectural roadmap for AI acceleration. Six concrete hardware exten-
sions are proposed — fused MAC instruction, SIMD int8 packed operations, sys-
tolic array co-processor, hardware activation functions, DMA-based data stream-
ing, and binary neural network support — providing a clear pathway from the
current general-purpose multicore to a lightweight dedicated AI accelerator.
6.2
Limitations
The following limitations of the current work are acknowledged:
• The 4-stage core does not implement the RISC-V M extension; convolution relies
on a slow software multiply routine (∼30 cycles per multiplication).
• The 64 KiB BRAM per core limits the deployable model size to approximately
34K parameters; larger models would require external DDR3 access.
• The CNN deployment processes one pre-compiled static test image per run; no
real-time camera input is integrated.
• Per-layer execution time on the RV32I workers is not instrumented; the MiBench
evaluation hardware counters were not applied to the CNN layers.
• The FruitCNNSmall model was trained exclusively on the clean white-
background Fruits-360 dataset; classification accuracy may degrade on cluttered
real-world images.
• Soft-float arithmetic in the dequantization step accounts for a significant fraction
of worker execution time, limiting the practical speedup of the CNN application.
• Scalability remains constrained by AXI interconnect contention at 8 cores, as
demonstrated by sub-linear efficiency in the MiBench results.
6.3
Future Work
Future work is organised from near-term to long-term:
Near-term:
• Add the RISC-V M extension to the 4-stage pipeline to enable hardware multiply
and eliminate the soft-multiply bottleneck.
• Instrument per-layer CNN execution time using the existing CSR cycle counter
infrastructure.
chapter: 06
28
• Integrate the PYNQ-Z2 camera interface to enable real-time image input and
live inference.
• Implement AXI-DMA based data transfer from DDR3 to worker BRAMs to
overlap data loading with ARM-side computation.
Medium-term:
• Add a fused MAC custom instruction using DSP48E1 slices, targeting a 10×
convolution speedup.
• Implement SIMD int8 packed dot-product operations for an additional 4×
throughput gain.
• Retrain FruitCNNSmall with data augmentation (random crop, flip, colour jitter)
to improve robustness to real-world images.
• Extend the model to a larger subset of the Fruits-360 dataset using model com-
pression or knowledge distillation.
Long-term:
• Design and integrate a small systolic array co-processor IP (e.g., 4×4 PE array
using 16 DSP48E1 slices) for dedicated convolution acceleration.
• Explore binary neural network variants using XNOR-popcount operations na-
tively supported by the RV32I ISA, requiring no hardware modification.
• Port the multicore system to a larger FPGA platform (e.g., Zynq UltraScale+)
to increase core count and BRAM budget for deeper models.
• Compare the extended system against dedicated NPU IP cores such as the Vitis
AI DPU on the same FPGA platform.
